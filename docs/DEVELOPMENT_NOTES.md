# 개발 참고 및 결정 기록

최종 갱신: 2026-10-07 (Asia/Seoul)

이 문서는 개발 중 발견한 주의사항, 결정 이유, 미결정 항목을 계속 갱신하는 작업 문서다. 단계별 범위는 [개발 계획](DEVELOPMENT_PLAN.md), 현재 작업은 [인수인계](SESSION_HANDOFF.md)를 참고한다.

## 1. 잊으면 안 되는 원칙

- LifeEvent Store가 중심이다. UI가 소스 데이터를 직접 받아 독자적인 상태를 만들지 않는다.
- Raw를 먼저 저장한다. 파서 실패가 수집 성공한 원본의 손실로 이어지면 안 된다.
- Raw 저장과 정규화 저장 사이의 중단을 복구해야 한다. 처리 상태, 커서, 버전 등 구체적인 방법은 Phase 1에서 결정한다.
- LifeEvent와 그 태그·엔티티의 갱신은 부분 반영되지 않게 트랜잭션 범위를 정한다. Raw 보존 자체를 파싱 성공에 종속시키지 않는다.
- 알림 삭제는 생활 사건 취소와 다르다. 결제·예약의 취소는 실제 내용으로 판단한다.
- 재처리 후 없어진 파싱 결과나 변경된 타입의 처리도 정의한다. 단순 추가만 하면 중복·오래된 결과가 남는다.
- 실제 알림/건강 원문을 로그, 테스트 fixture, Git 문서에 남기지 않는다. 수집 범위, 로컬 데이터 삭제 및 백업 포함 여부는 구현 전 결정한다.
- 빌드 성공은 실기기 수집 성공의 증거가 아니다.

## 2. 데이터 식별과 이력

다음 식별 개념을 혼용하지 않는다.

| 개념 | 역할 |
|---|---|
| source_key | 외부 원본의 논리적 식별자 |
| hash | 수집 시각 같은 가변 메타데이터를 제외한 원본 내용 변화 감지 |
| raw_event.id | 수집하여 보존한 특정 원본 버전 참조 |
| life_event.sourceId | 정규화 이벤트 식별, 필요하면 하위 이벤트/회차 식별 포함 |
| life_event.id | 앱 내부 이벤트 ID, 갱신 시 유지 |

Raw의 단순 `source_key + hash` 중복 제거만으로 충분한지는 검증이 필요하다. 내용이 A → B → A로 바뀌는 경우 동일 내용의 재수집과 실제 상태 복귀를 구분해야 한다. 내용 해시만으로 정규화 이벤트 ID를 만들면 수정 시 새 이벤트로 늘어날 수 있다.

Calendar 회차, 알림 키 재사용, 한 Raw에서 여러 이벤트 생성, sourceId가 없는 이벤트를 각각 테스트한다. UNIQUE(sourceType, sourceId)만으로 nullable 이벤트의 중복이 해결되는 것은 아니다.

## 3. 시간과 집계

- occurredAt은 생활 사건 시각, receivedAt은 앱이 수집한 시각으로 구분한다.
- 종일 일정은 날짜 의미를 보존한다. 모든 날짜를 무조건 단말 시간대로 변환하지 않는다.
- 일정 시각 변경으로 날짜가 이동하면 이전 날짜와 새 날짜의 집계를 모두 무효화한다.
- 수면은 시작일/종료일 중 귀속 기준을 정하고 화면 문구와 일치시킨다.
- 자정을 넘는 운동과 걸음 구간의 날짜 배분을 정의한다.
- 결제 취소와 부분 취소의 금액 반영 기준을 정한다. 다른 통화를 환율 정책 없이 합산하지 않는다.
- STEP은 원본 기반 기록, STEP_SUMMARY는 기간 집계로 구분한다. 집계 시 둘을 중복 합산하지 않는다.
- 미수집, 부분 수집, 권한 없음, 오류와 정상 0을 구분한다.
- 브리핑 7일 평균은 유효한 데이터가 있는 날짜를 기준으로 하고 표본 부족을 표시한다.
- 원본 변화 시 파생 데이터의 갱신 또는 재생성 정책이 필요하다. BRIEFING을 자신의 입력 집계에 다시 포함하지 않는다.

## 4. Android 소스별 주의사항

### Calendar

반복 일정은 Instances의 회차를 고려한다. 반복 예외, 시간 변경, 종일 일정, 계정 변경을 검증한다. 부분 조회 실패나 조회 기간 밖이라는 이유만으로 기존 이벤트를 삭제하지 않는다.

### Notification

앱에서 접근 가능한 필드를 최대한 보존하되 직렬화 가능한 형태와 한계를 명시한다. 과거 알림 전체 복원이나 시스템이 제공하지 않는 민감 내용 수집을 전제하지 않는다. 지속 알림, 그룹 요약, 내용 갱신의 중복 정책을 실제 샘플로 검증한다.

### Health Connect

기기 지원 여부, 권한, 조회 가능 기간, 백그라운드 접근 제약을 구현 시 공식 문서와 대상 단말에서 다시 확인한다. 걸음 합계는 다중 소스 중복을 고려한 aggregate API를 활용한다. 원본 기록 저장과 사용자 표시 합계의 계산 경로를 분리하고 집계 근거를 추적한다.

### WorkManager

정확한 시각 실행을 보장하지 않는다. 재시도와 앱 실행 시 누락 보완을 설계한다. 중복 작업 등록을 피하고, 실제 수집/반영에 성공한 범위 이후로만 처리 커서를 전진시킨다.

## 8. 2026-10-07 — MVP 구현 결정 및 유지할 계약

상태: 구현됨. 검증 범위는 VERIFICATION.md 참고. 사용자 요청에 따라 Phase 1~8 전체 기능을 구현했고 디자인은 기본 Material 3로 유지했다.

- 패키지 com.lifedashboard, min/target/compile SDK 35/36/36. JDK 21, Gradle 8.14.3, AGP 8.13.2, Kotlin 2.2.21. 버전 상세는 README에 유지한다.
- 5개 Room 테이블만 사용한다. 처리 상태와 수집 커서는 SharedPreferences, dirty 집계 상태는 daily_summary.updatedAt=0으로 표현한다.
- Raw는 sourceType+sourceKey별 증가 revision으로 보존한다. 직전 Raw의 JSON(occurredAt 포함) 해시가 같을 때만 재사용한다. A→B→A는 3개 버전으로 보존된다.
- 원본 payload는 raw_event에, 구조화 필드는 life_event.dataJson에 둔다. 원본 record 전체를 LifeEvent JSON에 중복 저장하지 않는다.
- 재분석은 원본 키별 최신 버전을 대상으로 한다. 과거 버전은 남기되 현재 이벤트를 과거 상태로 덮어쓰지 않는다. MVP 파서는 원본당 대표 이벤트 하나를 만든다. 복수 사건 지원 시 sourceId 하위 키와 제거된 파싱 결과 처리까지 함께 확장한다.
- Raw 저장과 정규화 트랜잭션을 분리한다. rawEventId가 최신 Raw와 다르거나 알림 parserVersion이 바뀌면 자동 복구한다. JSON 분석 실패는 원본을 남기고 다른 원본 처리를 계속하며 실패 건수를 표시한다.
- LifeEvent, 태그, 엔티티, dirty 날짜 표시는 하나의 트랜잭션이다. 변경 전후 날짜를 모두 dirty 처리한다. 시간대 변경 시 집계를 전부 다시 계산한다.
- status는 ACTIVE/CANCELLED/DELETED/NO_DATA/UNVERIFIED를 사용한다. 삭제 이력은 Raw tombstone 버전으로 남기고 Timeline에서는 DELETED를 제외한다.
- 일반 일정의 sourceId는 Event ID, 반복 회차는 Event ID+BEGIN이다. 반복 회차 이동은 이전 회차를 삭제 상태로 남기고 새 회차를 만든다. 일반 일정 이동은 같은 LifeEvent ID를 유지한다.
- Calendar는 접근 가능한 모든 캘린더의 최근 30일~향후 90일 Instances를 조회한다. 전체 조회 성공 후 조회 구간 안의 누락만 삭제 상태로 반영한다. 실패/권한 철회 시 삭제 추론을 하지 않는다.
- 알림은 앱 자신의 알림을 제외하고 접근 가능한 알림을 저장한다. 그룹 요약·지속 알림은 일반 NOTIFICATION으로 보존하며 결제 등으로 분류하지 않는다.
- 알림 키의 최초 postTime을 활성 수명 동안 보존한다. 내용 갱신은 동일 LifeEvent 갱신, 제거 후 재게시된 알림은 새 사건이다. 활성 키를 SharedPreferences에 보존하여 재연결 시 중복을 줄인다. Listener 종료 전 아직 저장하지 못한 순간의 알림까지 무손실이라고 보장하지 않는다.
- 알림 원문의 일반 필드와 extras를 저장한다. OS가 제공하지 않거나 Parcelable을 완전 직렬화할 수 없는 필드는 원본 바이너리까지 보존하지 못한다.
- Health는 걸음·수면·운동 읽기 권한 모두가 필요하다. 최근 29일 시작부터 현재까지 페이지 조회하고, 변경 토큰으로 이전 기록의 갱신·삭제도 반영한다. 커서는 모든 처리 성공 후에만 저장한다.
- 변경 토큰 만료 시 최근 구간 재조회로 복구하며 이전 기간의 정합성은 미확인으로 상태에 표시한다. 조회 가능 범위 밖의 걸음 변경을 알게 되면 기존 STEP_SUMMARY를 UNVERIFIED로 두어 오래된 합계가 정상 표시되지 않게 한다.
- 걸음 합계는 Health Connect aggregate(COUNT_TOTAL) 결과만 사용한다. STEP 원본을 더하지 않는다. 데이터 없는 응답은 NO_DATA이며 실제 0과 구분한다.
- 수면은 종료일에 귀속한다. 수면 단계가 있으면 sleeping/light/deep/REM 구간만 합치고, 없으면 세션 길이를 사용한다고 기록한다. 중복 세션 구간은 병합한다.
- 운동은 날짜 경계로 분할하고 겹치는 구간을 합친다. 브리핑 평균은 어제 이전 7일 중 기록 있는 날을 사용하며 3일 미만이면 비교하지 않는다.
- 결제는 KRW 정수 금액을 사용하고 취소 알림을 음수 움직임으로 집계한다. 타 통화를 임의 환산하지 않는다. 일부 금액이 모호하면 일반 알림으로 남긴다.
- Timeline은 하루 범위, 최신순, 동일 시각 ID순으로 조회한다. 100건씩 더 볼 수 있다. 수면은 종료일, 운동은 겹치는 날짜, 종일 일정은 calendarDate 기준으로 조회한다.
- 브리핑은 DERIVED + briefing:YYYY-MM-DD로 날짜별 1개 갱신한다. 입력 집계 시각·기간·시간대를 JSON에 남긴다.
- WorkManager는 6시간 주기 수집, 오전 7시를 첫 목표로 하는 24시간 주기 작업, 알림 후 파생 데이터 갱신을 담당한다. 정확한 시간 실행은 보장하지 않으며 앱 실행 시 보완한다.
- 최초 수집은 명시적 이용 동의 후 시작한다. 자동 백업 및 기기 이전을 제외하고 인터넷 권한을 선언하지 않는다. 전체 삭제는 앱 내부 데이터를 삭제하고 수집을 중지하며 외부 원본은 건드리지 않는다.

### 남아 있는 기술적 한계

- 집계는 dirty 날짜만 갱신하지만 계산 입력은 현재 전체 LifeEvent를 한 번 읽는다. 대용량 실측 후 날짜 범위 DAO로 좁힐 수 있다. Dashboard는 저장 집계만 읽는다.
- 실제 앱 알림 형식은 다양하므로 익명화한 실제 샘플 확보 후 오탐/누락을 계속 보완해야 한다. 현재 규칙의 인식 범위를 모든 앱으로 일반화하지 않는다.
- 초기 schema v1은 아직 공개 배포되지 않았다. 첫 설치 이후 스키마를 바꾸면 버전 증가와 migration이 필요하다. 파괴적 migration은 사용하지 않는다.

## 21. 2026-10-08 — 일정 중복 정리

- 같은 sourceType/sourceId는 기존 unique index와 ingest가 이미 중복을 방지한다. 다른 원본 ID의 복제 일정은 기존에 별도 ACTIVE로 표시되므로 내용 기준 대표 선정을 추가했다. 사용자 단말 원본에 대한 직접 진단은 미수행.
- 비교 기준: 제목 앞뒤/연속 공백 정리 + 시작/종료 시각 + 종일 여부. 종일은 UTC 기준 시작/종료 날짜를 사용한다. 반복 일정의 발생 날짜가 다르면 별개다.
- 장소(summary)는 공백을 정리해 비교하며 명시된 장소가 다르면 별개 그룹이다. 장소 없는 복제본은 첫 장소 그룹에만 연결하므로 다른 두 장소가 빈 장소를 통해 합쳐지지 않는다. 장소가 있는 항목, 먼저 생성된 항목, sourceId/id 순으로 대표를 정한다.
- Raw와 source별 LifeEvent/ID를 보존하고 중복 행만 DUPLICATE로 둔다. 타임라인은 중복을 제외하며 ACTIVE 기반 일정/집계/브리핑도 한 건만 반영한다. DB schema v1 유지.
- 정규화 트랜잭션에서 변경 전후 시작 시각/종일 날짜 후보를 재조정하고 dirty 집계 처리. 대표 변경/삭제 시 남은 복제본을 ACTIVE로 복원한다. 수집 삭제 감지는 DUPLICATE와 CANCELLED 일정도 포함한다.
- recoverPending에서 기존 저장 중복도 정리한다. 수집 활성 상태 새로고침 또는 저장된 원본 다시 분석으로 반영한다. 취소/삭제 상태는 ACTIVE 중복 대표 후보에서 제외한다.
